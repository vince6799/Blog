2026 年，代码补全和 Coding Agent 已经是两类工具。前者主要在编辑器里续写代码；后者会读取仓库、调用终端、修改多个文件、运行测试，并把改动交给 Git。Copilot、Cursor 式补全仍有用途，但本文讨论的是后一类。

四个项目的产品边界不同。Claude Code 与 Codex 可以安装后直接工作；Pi 提供一套较小的默认 Agent，也保留 SDK 和扩展接口；DeepSeek Harness 把模型适配器、工具、Agent loop、会话和 UI 都放进插件系统。选型时除了代码质量，还得确认运行时由谁维护、权限在哪里控制、模型能否替换，以及升级失败后由谁收拾。

核对基线：本文资料核对于 2026 年 8 月 18 日。DeepSeek Harness 仍处于 Developer Preview，并明确提示会有破坏性变更；Pi 已迁移至 Earendil Works。本文讨论的是 DeepSeek 官方 dsh、Claude Code、OpenAI Codex 与 Pi Agent Harness。快速演进的版本、套餐和模型清单应以购买或部署当日的官方页面为准。

先分清四个项目交付了什么

“Coding Agent”这个名称覆盖得太宽。对个人开发者，安装后能否直接修复代码最重要；对平台团队，更重要的可能是能否更换 loop、接入内部权限系统，或者统一调度已有工具。下面先按实际交付物拆开。

  • Claude Code：Anthropic 提供的端到端产品。终端、IDE、桌面和 Web 共用同一套引擎，模型、权限、会话与扩展机制一起演进。
  • OpenAI Codex：横跨本地 CLI、IDE、桌面与云端任务的产品体系。CLI 代码以 Apache-2.0 开源，但服务、账号额度和官方模型仍属于 OpenAI 产品生态。
  • DeepSeek Harness：用 Cordis 组合模型、工具、loop、会话、沙箱与 UI 的元框架。默认产品可以直接运行，但架构价值主要来自替换这些部件。
  • Pi Agent：默认只有读、写、编辑与 Bash 等核心工具的终端 Agent，同时提供 TypeScript SDK、RPC、扩展、Skills 与 packages。项目把复杂能力留给用户按需安装，不放进默认发行版。

Claude Code 和 Codex 的默认配置最多，团队较少碰运行时内部。dsh 暴露的部件最多，使用方也要承担更多集成与兼容工作。Pi 位于中间：默认循环可以直接用，缺少的能力再通过扩展补上。

场景落地：你到底需要哪一款？

场景 A：选 Codex

依赖 OpenAI 生态，希望本地与云端任务连成一体

为什么选：不要再用“搭载 o3/o4”概括 Codex。截至本文核对日，OpenAI 官方模型目录已经把 o3 标为被 GPT-5 系列接替，Codex 也有面向 agentic coding 的新模型。更实际的优势是同一个任务可以在 CLI、IDE、桌面与云端执行环境之间流转。这对已经使用 ChatGPT 企业账号、OpenAI 模型和 GitHub 工作流的团队比较省事。

Codex CLI 本地读取仓库、执行命令，云端 Codex 则适合并行、长时间运行或由 GitHub 事件驱动的任务。对复杂迁移、算法实现和需要多轮验证的改动，推理模型只是基础，沙箱、审批、任务交接和可恢复执行才是日常效率来源。

代价：官方体验仍围绕 OpenAI 的账号、模型可用性和额度策略。CLI 的开源不自动消除服务端依赖，也不保证任意 OpenAI-compatible 模型都获得同样表现。企业采购前要实测并发任务、模型可用区、数据控制和限额，而不是只看一次对话质量。

场景 B：选 Claude Code

重视自然语言协作、跨文件重构与成熟的扩展面

为什么选：Claude Code 把读仓库、改文件、跑命令、Git 操作和 PR 流程做成一致体验。官方文档列出的终端、IDE、Desktop 与 Web 并不是四套互不相干的壳；项目指令、MCP 与设置可以跨多个交互面复用。Skills 和 Hooks 适合固化团队流程，Agent SDK 与 Agent teams 则把它从个人工具推向可编排系统。

“代码更像人写的”很难脱离仓库和评分规则客观证明。更可靠的判断方式，是拿团队真实任务做盲测：跨十个文件的重构能否维持既有抽象、是否主动跑对测试、reviewer 需要改多少行、失败后能否定位根因。

代价：Claude Code 使用 Claude 模型。通过 AWS Bedrock、Google Vertex AI 或 Microsoft Foundry 接入，解决的是采购、区域和云治理问题，不是切换到非 Anthropic 模型，也不等于把 Claude Code 完整部署进自己的 VPC。长会话、并行 Agent 和大仓库扫描还会更快消耗订阅额度或 API 预算。

场景 C：选 DeepSeek Harness

要造公司的 Agent 运行平台，而不只是采购一个编码助手

为什么选：dsh 的核心命题是“Everything is a Plugin”。模型传输、工具注册、Agent loop、会话日志、权限、沙箱和 Web UI 都进入 Cordis 的依赖与生命周期系统。团队可以用 Profile 与配置 patch 组装不同运行环境，也可以把实现 ACP 等协议的外部 Agent 接成子 Agent provider；Claude Code、Codex 能否被调度，取决于对应适配器、认证和许可配置，并非一句“原生挂载”就自动成立。

Trajectory 视图与 append-only 会话日志让提示、工具调用和恢复路径更容易检查。这对评测、回放、审计和异构 Agent 实验很有价值。模型供应商或本地集群的切换也被放在明确的适配层，而不是散落在业务代码里。

代价：官方仓库仍明确标注 Developer Preview，并警告会发生破坏性变更。默认 Web UI 端口是 3080，不是常被二手文章写成的 3018。所谓“四级权限隔离”也不是官方固定产品规格：dsh 提供可组合的权限、审批、sandbox 与 preset，但最终安全性取决于实际插件树、Host/Agent plane 边界以及外部进程如何启动。

场景 D：选 Pi Agent

喜欢极简终端，希望模型自由，但不想先搭一套平台

为什么选：Pi 默认只给模型少数核心工具，把模型选择、会话、上下文压缩和终端交互做稳。它支持多供应商 API、自定义 provider、SDK 与 RPC；接本地 vLLM、Ollama 或其他兼容服务时，是否可用主要由模型能力、协议兼容与硬件决定。Apple Silicon 上也可以通过本地服务接 MLX 模型，但 Pi 本身不是 MLX 推理引擎。

Pi 刻意不把 MCP、plan mode 和 sub-agent 固化为唯一内置实现，却允许 extension 注册工具、命令、事件和界面组件，也能通过 package 分享 Skills 与 prompts。对单仓库维护、一次性脚本、SSH 环境和希望审阅每一步的开发者，这种克制往往比一个大型控制台更顺手。

代价：“可 100% 离线”必须满足模型权重、推理服务、依赖和任务数据都不访问外网，不能仅凭使用 Pi 得出。Pi 默认也没有内置文件、进程、网络和凭据权限系统；若处理敏感仓库，应在容器、微型虚拟机或策略沙箱中运行，并审计第三方扩展。

网关配置与 API 成本治理

先确认协议，再改 Base URL

在 dsh 或 Pi 中接聚合网关、自建代理或本地推理服务时，至少要分别验证模型列表、流式输出、工具调用、推理字段、图片输入、取消请求与错误码。把 BASE_URL 指向一个声称“OpenAI compatible”的地址，只说明路径可能相似，不代表 Responses API、Chat Completions、Anthropic Messages API 和各家的工具调用细节完全等价。

# 示意：变量名以具体 provider/插件文档为准
export PROVIDER_BASE_URL="https://gateway.example.com/v1"
export PROVIDER_API_KEY="..."

# 先做小任务：流式响应 → 工具调用 → 取消 → 重试
# 通过后再让 Agent 修改真实仓库

密钥应放在环境变量、系统密钥链或 secrets manager 中，不要写进项目 YAML、AGENTS.md、会话分享文件或 Git 历史。第三方中转会看到提示、代码上下文和工具结果，因此需要按新增的数据处理方与供应链节点进行审查。

Timeout 不是越大越好

长程重构可能让单次流式请求持续数分钟，网关、负载均衡器和客户端的 idle timeout 确实需要协调。把上限设到 300 秒以上可以作为起点，却不能当通用答案。更重要的是区分总请求超时与“多久没有任何字节才断开”，并确认断线后是否能取消上游推理、是否会重复计费、Agent 是否会幂等重试。盲目把所有 timeout 拉到一小时，只会让僵尸请求更难发现。

网页免费版不是 API 额度

账号能聊天，不代表能调用 API。ChatGPT、Claude 或 Gemini 的网页/应用套餐，与开发者 API 通常是不同的产品、凭据和计费面。某些 Agent 支持用订阅账号登录，那是工具与供应商明确提供的认证路径，不能把网页 Cookie、会话 Token 或所谓“逆向 Key”塞进网关替代正式 API。

Free tier 也不适合按“零成本生产方案”设计。Agent 一项任务往往包含多次模型调用，RPM、TPM、并发和每日额度任何一项触顶，都会把完成一半的工作留在仓库里。生产使用应配置付费按量账户、预算告警、并发队列和失败恢复；个人试用也应先在干净 Git 分支上运行。

Prompt Caching 的正确经济学

大型仓库会在多轮调用中反复携带系统提示、工具 schema、项目规则和相同文件片段，Prompt Caching 正好降低这部分重复输入的费用与首 Token 延迟。但“节省 90%”通常描述的是某个供应商对缓存命中输入 Token 的单价折扣，不是整项 Agent 任务的总成本必然下降 90%。输出 Token、首次写缓存、未命中的动态上下文、工具执行和本地基础设施仍然计费。

  1. 保持系统提示和工具 schema 的顺序稳定，把变化快的会话内容放在后面，避免每轮重写固定前缀。
  2. 分别记录输入、缓存写入、缓存读取、输出、失败重试与子 Agent 成本，不要只看总 Token。
  3. 继续裁剪无关上下文。缓存降低的是价格和延迟，不会减少无关文件对模型判断的干扰。

总结：按使用方式做选择

  • 团队已经使用 OpenAI 或 ChatGPT，并希望在本地和云端之间分派任务，可以先试 Codex。
  • 团队偏好 Claude 的交互方式，并需要 MCP、Hooks、Skills 或 Agent SDK，可以先试 Claude Code。
  • 平台团队准备自行维护模型路由、loop、权限、会话和 UI，DeepSeek Harness 提供的改造空间最大。
  • 只需要一个轻量终端 Agent，并愿意自己选择扩展和隔离方案，Pi 更合适。

团队采购不适合用一道算法题决定。可以从真实仓库挑三项任务：跨模块重构、信息不完整的故障定位、带权限限制的自动化。统一记录任务是否完成、人工接管次数、错误改动、端到端时间、缓存命中和总成本。还要专门测试失败恢复：网络中断、模型限流或工具返回非法 JSON 后，仓库是否仍处于可理解、可回滚的状态。
